Install Android to a virtual disk

The VM window is open. Do these 6 steps once; after that ApkStart boots straight from the disk and needs no image.

  1. Boot menu: use ↓ to select Installation - Install Android-x86 to harddisk, then Enter
  2. Choose Partition: choose Create/Modify partitions; when asked about GPT, choose No
  3. cfdisk partitioning: New → Primary → press Enter for the size → Bootable → Write → type yes → Quit
  4. Format: choose vda1 → when asked to format, choose ext4 → Yes
  5. Bootloader & system: Install GRUB choose Yes; Install /system as read-write choose Yes
  6. Finish: when it reaches 100% click “I’ve finished installing” below (ApkStart restarts and takes over)

If adb later reports as disconnected: in the VM window press Ctrl+Alt+F1 to open a terminal, run setprop service.adb.tcp.port 5555, stop adbd, start adbd, then press Ctrl+Alt+F7 to return to the graphical UI.

Memory, core count, render backend, port and acceleration are all chosen automatically; a failed start is retried with a fallback, no manual tuning needed. ApkStart uses a dedicated adb server port 5044 (your own adb uses 5037), so from a terminal adb devices you cannot see this Android device — the isolation is intentional. To connect, use $env:ANDROID_ADB_SERVER_PORT=5044 and run adb again. Note: do not manually adb connect on port 5555; that pops the Allow USB debugging system dialog on top of running apps.

App windows
Press F11 at any time, or right-click the tray icon to switch; fullscreen only enlarges the window, keeps the aspect ratio and does not restart the app.
When enabled, opening an app fills the screen without pressing F11. Works best together with Landscape below — a landscape panel already matches the screen aspect ratio, so full screen leaves no black bars.
Android orientation follows the actual orientation of the virtual phone panel. When the panel orientation differs from the one the app declares, Android only gives the app a narrow strip in the middle with black bars on both sides — resizing the window or changing the resolution will not fill it. Follow app mode reads the app orientation when the APK is installed and switches the panel to match at launch, so apps like Hongguo Short Drama and Modu open upright and fill the screen. The runtime only restarts once when the orientation is wrong (about ten seconds), and apps in that orientation open instantly afterwards.
At 720 wide and 190dpi that is 606dp, just past the Android 600dp tablet breakpoint, so the two-column episode page in Hongguo Short Drama and the split settings pages only appear in this layout. Turning it off returns to phone layout (larger text, less information). Applies the next time an app is opened.
This is the current physical panel orientation in use, written automatically by the policy above. Only in forced mode is it entirely up to you.
Embedded mode looks most like one window per app, but it has to squeeze the emulator window into our own, which tends to show black bars or misplaced clicks when resizing, rotating or switching between windows. In detached mode orientation, scaling and input are handled natively by the emulator, so those problems do not occur, at the cost of one extra taskbar icon. Changes apply the next time an app is opened.
In window mode drag the border to resize freely; this sets Android’s internal render size, smaller is cheaper.
Mouse buttons
The emulator treats the left button as a finger tap natively; press and drag to swipe, nothing to configure.
By default the right button also counts as a tap (easy to trigger by accident). When enabled, the right button only goes back and never taps.
Smooth mode merges wheel ticks within a short window into one swipe gesture, so it doesn’t stutter and doesn’t spawn an adb process per tick.
Side-button mapping needs a global mouse hook. The hook is installed only while an ApkStart app window is focused and removed on blur or close, so it never slows the desktop.
These mappings only apply while an app window is focused; back on the desktop or after closing the window, mouse behaviour is fully native Windows.

Points Android at public CN DNS servers (Alibaba / Tencent). By default Android uses the host’s DNS; with a VPN or corporate network, lookups can take hundreds of ms and video apps start slowly. Turn off if internal domains misbehave.

Container details (advanced)
Caps the vCPU quota and lowers process priority so the Windows desktop gets CPU first. The “Resource profile” above already sets this.
Game mode keeps the Android VM at a higher CPU priority and reduces host-side polling, minimising input and frame latency; other programs on the machine get slower. The container still drops priority when no app window is open.
Also disables Play Store, setup wizard, print service and other background packages, keeping only what apps need. Turn it off and they are restored automatically if an app complains about missing Google Play services.
ApkStart boots the Android environment in the background right after launch (the window stays hidden, you never see the emulator). Opening any app then costs one “open” — measured from 20+ seconds down to almost nothing. Costs ~1 GB of RAM while idle; with it off, the first app launch is a cold boot.
Android boots once and stays resident; opening an app no longer re-runs the system, it just starts that app and stops the others. Closing the last window frees background processes and parks the container, and the next launch is still instant.
Download & update sources
“Auto” asks both GitHub and Gitee for the latest version, benchmarks every download URL with a real 256 KB probe, then downloads from the fastest one; one source being unreachable doesn’t break updates.
When direct GitHub is too slow, also benchmark the public ghfast.top / gh-proxy.com proxies (they only forward public release files, no accounts). Off means direct connections plus your own prefix only.
When set, only your prefix is used and the two public mirrors above are skipped; leave empty to let “Auto” decide. The downloader prepends it to the real URL.
Large files download in parallel chunks. 8 threads already saturate most home connections; try 16 on a stable line.
Gitee update source (optional)
This repo is public and Gitee’s release list can be read anonymously, so leaving it empty still uses the Gitee source. Fill it only if Gitee rate-limits you (403/429) or you want a private fork: gitee.com → Settings → Private token, tick only “projects” — it is used to read the release list and never uploads anything.
This PC checkup · auto-config
Checks this machine first: is CPU virtualization on, is the Windows Hypervisor Platform installed, what GPU it has and how much VRAM, and are memory and the OS version enough. Anything that can be changed automatically (memory / cores / quality / render backend) is written straight into settings, and the result is saved as a driver; things that need administrator rights get a button; things that can only be changed in the BIOS are explained.
Drivers · compatibility patches
Some machines only run after launch options are changed (old GPUs with low GLES versions, hardware acceleration off, a driver version that crashes hardware rendering). A driver is a JSON file: it declares which machines it matches and which launch options to change when it matches. You can write, import and share your own. Drivers only change whitelisted launch options, run no code at all; if nothing matches, they do nothing.
Reading drivers…
Export this PC template fills in the match conditions for this machine; change effect in gpuMode / forceTcg and it works. Field docs are in docs/drivers.md.

Runtime
ApkStart only runs its own runtime: adb / emulator / system images are all downloaded and managed by it. It does not detect, take over or depend on any emulator installed on your PC (MuMu / LDPlayer / BlueStacks / WSA are never used). So switching machines, whether others have an emulator installed, or how emulators update, makes no difference here.
